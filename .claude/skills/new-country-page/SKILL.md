# World Mappy 新規国ページ執筆スキル

新しい国のページ（`<country>.json` → `generate.py`でHTML生成）を一から書き起こすときに使う。CLAUDE.mdには常時守るべき制約（文字数ルール・廃止済みフィールド・overview同期方向など）だけが残っており、「ゼロから1本書き上げる」ときの設計方針はここに集約している。

**必ず`assets/tools/_country_template.json`を実際に開いて、その構造に沿って埋めていくこと。** このスキルは各セクションの「なぜそう書くか」の方針を説明するもので、JSONスキーマそのものではない。ビルド手順・フィールドの技術的な意味は`assets/tools/generate.py`のdocstringを参照する。

新規国を1本仕上げるときの作業順序の目安:
1. `overview`（基本情報カード群）→ 2. `basic_data` → 3. `courses`（モデルコース）→ 4. `spot_sections`/`food_items` → 5. `spot_points` → 6. `season` → 7. `budget`/`practical` → 8. `phrases` → 9. `index_card.catch`・`index.html`の`tags` → 10. `overview.flag_html`・各`prompt_en`

以下、セクションごとの方針。

## 1. courses（モデルコース）

`courses.stable_plans[]`は配列だが、**3段階の温度差**で統一する:

- **プラン1（配列の最初）**: 拠点を絞って身軽に周る初心者・王道向け。ホテル連泊が基本、スーツケース移動は少なめ。
- **プラン2以降**: プラン1より一段階、行動範囲を広げる。「一都市一泊」「新幹線で縦断」のような移動を伴うルート。**わざわざ「バックパッカー向け」と銘打つ必要はない**——移動を増やす設計にすれば自然とその色になる。
- **`adventure_plan`（`stable_plans`とは別の単数フィールド）**: 冒険枠。ページ最下部の専用スロットに必ず表示される。管理人の実体験ルートがあればそれを書き（南アフリカの前例）、なければ一般的な「上級者向けの尖ったルート」（台湾の環島、マレーシアの半島縦断のような）を書く。

理想形は台湾の3段構成: 週末プラン（3泊4日・拠点集中）→縦断プラン（5泊6日・移動多め）→環島（adventure_plan・上級者の憧れルート）。

### タイトルの書き方
- `courses.stable_title`は毎回書き下ろす。「定番の2大プラン」のような中身を説明しない汎用文言にしない。プラン1・2に共通するスタイルが一言で伝わる見出しにする（例:「拠点を絞ってじっくりプラン」）。
- `stable_plans[].title`には**そのプランで実際に訪れる都市名を全て列挙**する（例:「バンコク・アユタヤ」「KL＋ペナン」）。「〇〇満喫」のような都市名を含まない抽象タイトルにしない。

### 語尾トーン（体験談風にしない）
`courses`内の全テキスト（`content_html`/`summary`/`tip`含む）は、**「管理人がすでに行ったかのような一人称・過去形の締め」を使わない**。「〜な旅になった」「〜と感じた」「〜が正解だった」のような回想調は禁止。プラン紹介の締めは「〜する密度の濃いプランである」のように客観的・現在形・体言止めにする。

- 例外1: 町や土地の**歴史**を述べる過去形（「かつては漁業で栄えた港町だった」）はOK。「朝食を楽しんだ後、〜へ」のような行程の「〜した後」も普通の指示表現なのでOK。
- 例外2: 南アフリカの`adventure_plan`だけは実体験の一人称回想として意図的に残されている。中立化しない。

チェック方法: `courses`を再帰的に走査し、各文（`。`区切り）の末尾が過去形・体験談調（`〜になった`/`〜だった`/`〜はず`/`〜した旅`等）で終わっていないか確認する。`content_html`だけでなく`tip`・`summary`等の全フィールドが対象。

### 移動の表現（transit / transport_note / pre_transit）
- **日をまたぐ移動**（宿泊地が変わる）: `{"transit": true, "duration": "...", "train": true}`を日と日の間に独立行として挟む（矢印付き）。
- **同じ都市に戻る日帰り**（例: KL→マラッカ→KL）: 独立行にせず、その日のdayオブジェクトに`transport_note`（`pre_transit`と同形式）を追加する。矢印なしのアイコン付きボックスとして説明文の下に表示。
- **拠点が変わり午前中に移動**（例: 台北前泊→翌朝花蓮へ）: 到着日のdayオブジェクトに`pre_transit`を追加。Dayバッジ直後・説明文の直前に矢印なしで表示。
- **拠点が変わり午後に移動**（例: 台南観光後に高雄へ）: 従来通り独立`transit`行を前の日の直後に挟む（矢印付き）。

判断基準: 前後の`transit`の`duration`が「その日の観光と地続きの移動」なら`transport_note`/`pre_transit`、「宿泊地を移す移動」なら独立`transit`行。

アイコンフラグ: `plane`/`taxi`/`ferry`/`walk`/`train`（新幹線・高速鉄道など明示的に高速鉄道と呼べるものだけ）/`local_train`（🚆、在来線・普通列車）。どれも立てなければバス扱い。**`country_template.html`側のこの分岐は`stable_plans`用と`adventure_plan`用で2箇所に重複定義されている**ため、テンプレート側を修正する場合は両方に反映すること。

### courses.introの型
```
[直行便時間・時差など基本情報]の[国名]は「[その国らしい旅の強み]」のが最大の強み。
初めてなら[エリア]に絞った<strong>[プラン1名]</strong>、
[2回目以降/連休が取れるなら]は[内容]を巡る<strong>[プラン2名]</strong>がおすすめ。
（adventure_planへの一言布石。国ごとに書き分ける。定型文にしない）
```
冒頭の「強み」の一言（台湾＝短い休みでも成立する等）も国ごとに変える。直行便が少ない・遠い国は「便数は少ないが現地移動はコンパクト」のようなその国ならではの利点に置き換える。「どちらもアレンジ自由です」のような蛇足の締めは入れない。

## 2. phrases（フレーズタブ）

`_country_template.json`にある雛形の**カテゴリ構成・フレーズ内容をそのまま踏襲する**（ゼロから設計し直さない）。

- カテゴリは5つ固定: 「👋 あいさつ」(8項目) 「🙏 基本表現」(10項目) 「🍽️ レストラン・ショッピング」(10項目) 「🔢 数字」(2項目: 0〜5・6〜10) 「🆘 観光・トラブル」(3項目)。項目数は前後1〜2個ずれる程度の微調整はOKだが、カテゴリ自体を削ったり増やしたりしない。例外はその国特有の話題がある場合にカテゴリ名だけ差し替える（南アフリカの「🦒 サファリ・観光」）。
- 各`items[]`の`jp`（日本語の元の文）は雛形のままにする。翻訳者が変えるのは`foreign`（現地語）・`reading`（カタカナ読み）・`audio`（空文字のまま）の3つだけ。
- `multi`は基本`false`。英語圏＋現地語を両方見せたい場合のみ`true`にして`decks[]`を複数用意し、`active`をどちらか一方だけ`true`にする。

## 3. spot_points（観光のポイント）

- **件数は3個固定**。増やすとレイアウトが崩れる。書きたい項目が多い場合はテーマが重複しないもの・最も価値の高いものを優先して絞り込む。
- **3個のうち最低1個は`food_ref`（グルメ紐付け）にする**。既存の`spot_ref`項目のうち最も重要度が低いものをグルメに差し替える（安全上の注意喚起や国のハイライトになる目玉スポットは削らない）。すでに料理・屋台文化について書かれているが`spot_ref`のままの項目があれば、内容そのままに`food_ref`へ転換し本文に`showFood()`のキーワードリンクを追加してよい。
- `body`は120〜250文字程度。一文で終わらせず、背景情報や体験の具体性を2〜3文で書く。
- 画像は`image`パスを手打ちしない。代わりに参照先の`num`を`spot_ref`または`food_ref`として書く:
  ```json
  { "title": "...", "body": "...", "spot_ref": "SAM 01" }
  ```
  `generate.py`が生成のたびに参照先の`image`フィールドを`spot_points[].image`へ自動コピーする。画像がまだ無くても`spot_ref`だけ書いておけば、後で画像生成した瞬間に次の`generate.py`実行で自動反映される。

## 4. practical.hotel_intro（ホテルの選び方の冒頭説明）

- 文字数100〜180字程度。
- その国ならではの宿選びの「肝」を核にする。例: レンタカー周遊国（NZ・カナダ）は「観光ルート沿い・駐車環境」、鉄道が便利な国（台湾・韓国・タイ・ドイツ）は「駅近」、現金社会（ラオス）は「現金のみの宿が多い」、シルクロード都市（ウズベキスタン）は「旧市街の歴史地区・隊商宿改装ホテル」。
- **治安への配慮が必要な国**（南アフリカ・イタリア・スペイン・フィリピン・ベトナム・スリランカ等）は、「安さだけで選ぶと治安の悪いエリアに当たりやすい」「特に夜着の日程では初日くらい安心して休める立地を」という要素を一部含める。南アフリカは最優先で治安配慮を盛り込む。
- 治安が良好な国（台湾・シンガポール・NZ・カナダ・マレーシア等）は無理に治安警告を入れず、実用的な立地・予約タイミングのコツ中心でよい。
- 特殊枠: 北朝鮮は個人での宿予約・エリア選択ができないため、「宿選びより信頼できる催行会社のツアー選びが重要」という内容にする。
- 空欄にすると`country_template.html`側のフォールバックで旧固定文（治安への一般的な注意喚起）が表示されるので、新規国では必ず書き下ろす。

## 5. practical.special_note_*（目立つ注記ボックス）

**入国手続き関連の情報専用**の枠。ビザ免除条件の変更、電子渡航認証（K-ETA・ETA・TWAC・MDAC・SG Arrival Card等）の導入・要件、入国カードのオンライン化、子供連れ入国時の特別書類要件など「入国前に手続きが必要になる話」だけを書く。

**観光地の予約Tipsや治安の注意喚起は書かない**（治安は`prac_cards`の「治安」カードで既に扱っている）。空欄が不自然に見える場合（実在する電子入国システムがありそうな国）は、「特に無さそう」で済ませずその国特有のデジタル入国カード制度（NZTD・eTravel・TDAC等）を調べてから埋める。該当なしと確認できた国のみ空欄のままでよい。

## 6. practical.prep_steps（準備は早めにタイムライン）

以下の順序で統一する:
1. パスポート取得・更新（1〜2ヶ月前）
2. 海外対応クレジットカードの申込（1ヶ月前）
3. 航空券・ホテルの予約（国により時期は前後してよい）
4. 海外旅行保険の加入（出発前日まで）
5. SIM・ポケットWi-Fi（またはeSIM）の準備（1〜2週間前）
6. **国固有の入国関連手続き**（電子渡航認証等）があれば必ず最後に配置する

- `special_note`に既にある制度は`prep_steps`の最後にも短く案内する（`special_note`は詳細、`prep_steps`はリストの1項目として）。
- 治安・安全情報の確認のような入国準備と無関係な項目を最後に置かない。
- 色は`border_color`/`bar_color`/`timing_color`で緑→黄→オレンジ→赤のグラデーション。**最後の項目は`bar_color`を空文字にする**（線が続かないように）。
- 該当する入国関連手続きがない国は5項目のままで完結してよい（無理に6項目にしない）。

## 7. practical.tour_platforms / apps[]（ツアー予約サービス）

`tour_platforms`は自由記述ではなく、`assets/affiliates-data.js`の`AFFILIATE_CARDS`に定義済みのキー（`klook`/`getyourguide`/`viator`/`kkday`等）を**そのまま**配列で入れる。一致しない文字列を入れると中身のない空カードになる。

### 4社の選び方（規模順）
1位 Viator（Tripadvisor傘下、世界最大） / 2位 GetYourGuide（欧州発祥、欧米で強い） / 3位 Klook（アジア発祥、急成長） / 4位 KKday（台湾発祥、東アジア特化）。

| サービス | 得意エリア | 特徴 |
|---|---|---|
| Viator | 北米・ハワイ・グローバル | Tripadvisor連動、口コミ豊富、英語ツアー充実 |
| GetYourGuide | ヨーロッパ・アメリカ | 欧州の美術館・歴史ツアーに強い、UX高評価 |
| Klook | アジア全域 | 鉄道チケット・テーマパーク割引、日本語サポート充実 |
| KKday | 台湾・韓国・東アジア | Klookと並ぶアジア特化、現地発オリジナルツアーが多い |

**選び方の目安**: ハワイ・アメリカ・ヨーロッパ → Viator or GetYourGuide。韓国・台湾・東南アジア → Klook。地域適性が曖昧な国は2社併記してよい（NZ「viator, klook」、ラオス「klook, getyourguide」）。地域適性が明確な国（台湾・タイ→klookのみ、ドイツ・イタリア・スペイン→getyourguideのみ）まで無理に2社化しない。該当なしなら`[]`。

**`tour_platforms`に載せたサービスは`practical.apps[]`にも必ず対応するアプリ枠を追加する**（片方だけだと導線が片手落ちになる）。
- `icon`: `"klook"`/`"getyourguide"`/`"viator"`等のキー（`素材/絵文字/{key}.svg`を自動解決）。
- `name`: `"Klook（クルック）"`のような型。
- `affiliate`: 同じキー（`data-affiliate`でテキストリンクが自動描画される）。
- `desc`: その国の代表的な観光地・ツアー内容に触れた1文。
- `tour_platforms`が2社以上ある国は`apps[]`側も全社分追加する。

## 8. practical.country_items（国特有の持ち物）

`country_items_label`は`"🇽🇽 {国名}特有の持ち物"`の型（絵文字は国旗、`overview.flag_html`と同じ2文字国コード）。

`country_items`は5〜6項目。**一般的な持ち物チェックリストと重複する項目（パスポート・充電器・常備薬等）は書かない**。実績のある切り口: プラグ形状に合う変換アダプター、気候特有の装備（紫外線・乾燥・防寒・雨具）、その国特有のマナー対策（寺院での服装・脱靴）、感染症・虫対策、レンタカー移動が基本の国なら国際運転免許証。理由を括弧書きで添える（例:「サンダルまたは脱ぎやすい靴（寺院は入場時に脱靴が必須）」）。特殊枠の国（北朝鮮等）でも空欄にせず、その国ならではの必須事項を持ち物目線で言い換えて埋める。

## 9. overview系フィールドの文言統一パターン

- **`overview.visa`**: パターンA「不要（○日）」／パターンB「オンライン申請要（○日）。渡航前に{制度名}（{日本語説明}）への登録が必要です」（シェンゲン加盟国のETIAS等）／パターンC「{取得種別}取得要（○日）。{制度名}（{日本語説明}）をオンラインで事前取得（条件）」。太字本文（句点より前）に略称を置かない、略称と日本語訳は句点の後ろに回す。北朝鮮のような特殊枠は当てはめず実情通り。
- **`overview.timezone`**: 「日本 −N時間」（「日本」と符号の間に半角スペース）。サマータイムがある国は句点で区切って続ける（「日本 −8時間。サマータイム時は−7時間」）。時差なしは「時差なし」のみ。
- **`overview.language`**: 「{現地公用語}（英語は{通用度}）」の型。英語自体が公用語の国（シンガポール・南アフリカ・NZ）は「英語（公用語）」を主語にしてよい。`basic_data`の「言語」`value`は`overview.language`と自動同期されるので書かなくてよいが、`note`には言語学的なトリビアだけ書く（英語の通用度を重複させない）。
- **`overview.flight_hours`**: 直行便がある国「直行便で約○時間」（乗継便もあれば「（乗継便あり）」、具体的な所要時間が分かる場合のみ「（乗継便は約○〜○時間）」）。直行便がない国「乗継で約○時間」（経由地・航空会社名は書かない）。北朝鮮のような特殊枠は「直行便なし」のみ。
- **`overview.budget_range`**: 「○〜○万円」のみ。泊数を書き添えない。
- **`overview.danger_level`/`danger_label`/`danger_note`**: レベル0は「特に危険情報なし」、レベル1は「レベル1：十分注意」で統一。`danger_note`は15〜35文字程度に要約し文末に句点を付けない（危険地域の州名・都市名を逐一列挙しない）。レベルの数値自体は外務省の実情通りに設定し、揃えるために動かさない。
- **`overview.currency_name`/`currency_rate`**: `currency_name`は「{通貨名}({略称})」で括弧は半角。`currency_rate`は「1{略称} ≈ {円}円」の型（桁が大きい通貨は「1万{略称} ≈」、極小額通貨は「1,000{略称} ≈」）。レートは`assets/tools/check_exchange_rates.py`で実勢と突き合わせる（対応国は`COUNTRIES`配列に追記が必要）。

## 10. difficulty_bar（旅行難易度バーの配色）

`difficulty_label`に応じて以下の4パターンに固定する。**国旗の色を流用しない**。

| difficulty_label | difficulty_bar | difficulty_label_bg | difficulty_label_color |
|---|---|---|---|
| やさしい | `linear-gradient(90deg,#00a86b,#66cc99)` | `#e8f5ee` | `var(--green)` |
| ふつう／普通 | `linear-gradient(90deg,#00a86b,#ffcc80)` | `#fff4e0` | `#b09000` |
| やや難しい／やや易しい | `linear-gradient(90deg,#ff9800,#ffcc80)` | `#fff3e0` | `#e65100` |
| 最難関 | `linear-gradient(90deg,#cc0001,#8a0000)` | `#fdeaea` | `#cc0001` |

`difficulty_pct`は0〜100で各国の実情に応じて設定してよいが色は表から外れないこと。`difficulty_desc`は廃止済みのフィールドなので書かない。

## 11. index_card.catch と tags

### catch（44〜54文字目安）
辞書的なキーワード列挙ではなく、その国の情景が浮かぶ描写的な一文にする。**一人称の実体験を装わない**（行ったことのない国も扱うため）。「〜な国」「〜が待っている」のような説明口調・図鑑的言い回しを避け、情景・匂い・音・光景を連想させる描写を1つ差し込む。**体言止めで終わらせない**（動詞・述語で終える）。**締めの動詞を既存の全`catch`と被らせない**——新しいカードを書く前に`index.html`の`COUNTRIES`配列にある全`catch`の文末動詞を確認し、被らない動詞を選ぶ（響き渡る/溶け合う/重なり合う等が既出なら、漂う/揺れる/通り過ぎる/満ちる/包み込む/沸き立つ/こだまする/弾ける等から選ぶ）。準備中（`available:false`）のプレースホルダーも同じトーン・文字数で書く。

`index.html`の`COUNTRIES`配列に手書きした値が実際に表示される値。`<country>.json`の`index_card.catch`は初回`update_index()`実行時にコピーされるだけで以後連動しないため、**両方**を書き換える。

### tags（コア8種＋個性タグ）
固定8種のコアタグ（`index.html`のフィルターチップと文字列完全一致が必要）: `ビーチ` `世界遺産` `グルメ` `自然` `都市` `リゾート` `歴史` `アウトドア`。

`tags`にはコアタグから**2〜4個**必須で含め、その国ならではの**個性タグを1〜2個**添える（例: 南アフリカ「サファリ」、台湾「夜市」、スリランカ「紅茶」）。個性タグは固有名詞・体験ワードにする——「大自然」「アドベンチャー」のようなコアタグの曖昧な言い換えは避ける（言い換えたければコアタグ本体を別途含めた上で追加する）。カード表示は先頭4個のみ使われるため、5個以上書く場合は見せたいものを先頭4個以内に収める。特殊枠（北朝鮮等）はコアタグ0個で実情に即した個性タグのみでよい。

## 12. overview.flag_html（国旗グラフィック）

**絵文字は使わない**（Windowsで正しく描画されない）。**座標を自分で計算・推測することも禁止**——過去に太極旗の角度を2回間違えるなど、検証しても実物とズレる問題が繰り返し発生したため、必ず以下の手順で検証済みSVGをそのまま流用する。

1. [`hampusborgos/country-flags`](https://github.com/hampusborgos/country-flags)（Wikimedia Commons由来、公式縦横比を維持）から対象国のISO 3166-1 alpha-2コードでSVGを取得:
   ```
   curl -s "https://raw.githubusercontent.com/hampusborgos/country-flags/main/svg/{cc}.svg"
   ```
   （`lipis/flag-icons`は全国旗を4:3枠に強制するため使わない。）
2. `viewBox`から縦横比を計算し、高さを`100px`に固定して幅を比率通りに算出する（3:2なら`width="150" height="100"`）。SVGの中身は一切書き換えない。
3. `<div style="display:inline-block;border:1px solid #eee;line-height:0;overflow:hidden">`で包んで`overview.flag_html`に入れる。
4. 反映後は`mcp__visualize__show_widget`で実際に描画確認する。

このライブラリに存在しない対象に限り、WebSearchで公式仕様を調べてPythonで座標計算する旧方式にフォールバックする（その場合も角度・位置を`atan2`等で数式検証してからプレビューに進む）。

## 13. prompt_en（画像生成プロンプト）

- **時間帯**: スポットの性質に合わせる。絶景・記念碑系は`at golden hour`/`at sunset`、市場・美術館・屋外散策系は`in the morning light`か指定なし、ナイトマーケット・バー街系は`at night`/`at dusk`。
- **人物**: 賑わいを出すのは歓迎だが、**特定の1人を主役に表情・手の動き・複雑なポーズを指定すると顔や手が破綻しやすい**。安全な組み合わせ「小さく・複数・匿名・単純な動作」:
  - `a few tourists in the distance` / `small figures for scale` / `silhouettes of visitors`（逆光・夕景と相性◎） / `crowds of people walking` / `a tiny hiker figure visible on the trail`
  - 職人の単純な動作（例: グラスブロワーが炉の前で作業）は比較的安全。
  - 避ける: クローズアップの人物指定、「〜のポーズを取る」「微笑みながら〜を持つ」等の具体的な表情・手の動き指定。

`hero_prompt`（ヒーロー画像）の人物有無は、風景寄り（テーブルマウンテンの空撮等、俯瞰・引きの構図）なら人物なし、観光スポット寄り（コロッセオのような定番の賑わいスポットを地上アングルで）なら人物あり（小さく・複数・単純な動作）で判断する。

## 14. basic_data / budget.items / cash_daily の実務ルール

- `basic_data[]`には**「通貨」の行を必ず入れる**（`value`は通貨名と略称、`note`は円換算目安を`overview.currency_rate`と揃える）。同じレートを`practical.prac_cards`の「通貨」カードにも追記する（`generate.py`が`overview.currency_rate`から自動同期するので手入力は`overview`側だけでよい）。
- `budget.items[].detail_html`は`<br>`区切りで**2行固定**が基本。各行15〜60文字程度。
- **`交通費（1日）`に都市間移動（国内線・レンタカー）のコストを混ぜない**——航空券という別枠が既にあるため二重計上になる。滞在中の都市部の日常的な移動（バス・地下鉄・タクシー・配車アプリ）だけを反映する。国内線・レンタカーが必要という情報自体は`detail_html`に注記として残してよいが金額には含めない。
- **`practical.cash_daily_low`/`cash_daily_high`は全国共通の計算式で機械的に算出する**（個別の現地情報での上書きはしない）:
  1. 「食費（1日）」の`price`は**中央値**（下限と上限の平均）を取る。「交通費（1日）」も基本は中央値だが、`detail_html`の上限側が国内線・レンタカー・隣島船のような都市間・地域間移動を指す場合は**下限のみ**を使う（大口移動費が現金の目安に混入するのを防ぐため）。
  2. `practical.cash_dependency`に応じて係数を掛ける: `低`（カード・タッチ決済中心）×0.2 / `中`（都市部はカードOKだが屋台・市場は現金中心）×0.7 / `高`（現金がないと困る）×1.0。
  3. `overview.exchange_rate`で現地通貨に変換した値を`cash_daily_low`とする。
  4. `cash_daily_high`はさらに3割ほど上乗せして切り上げる（両替忘れ・予定外の出費への備え）。
  5. 現地でよく流通する紙幣単位に合わせてキリの良い数字に丸める。
